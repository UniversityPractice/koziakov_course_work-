## 1. Зачем и что считается успехом

Приложение — это практическая часть курсовой по «Проектированию баз данных». Оно показывает, что спроектированная база работает: сотрудник салона через окна вводит, меняет, удаляет и просматривает данные, оформляет заказы и получает ответы на 7 вопросов задания. Скриншоты приложения идут в раздел 3.6 записки.

Успех, если:
- выполнены все жёсткие требования задания (раздел 2);
- каждый сценарий проверки из раздела 9 реально прогнан, и результат записан;
- код настолько простой, что студент может объяснить на защите любую строку.

**Антицели**, то есть то, что считается провалом, даже если приложение работает:
- в коде есть ORM, f-строки или конкатенация в SQL;
- SQL разбросан по модулям, а не собран в `sql.py`;
- логика базы продублирована в Python: пересчёт остатков, подстановка цен, формирование заявок;
- лишние слои, паттерны, фреймворки. Студент не сможет объяснить, «зачем тут этот класс».

## 2. Жёсткие требования

1. Только нативный SQL через `psycopg2`, без ORM.
2. В интерфейсе есть ввод, редактирование, удаление и просмотр данных.
3. Первичные ключи выдают последовательности. Приложение никогда не передаёт `id` в `INSERT`, а новый ключ получает через `RETURNING id`.
4. Приложение выполняет все 7 запросов задания.
5. Рекомендуемая цена букета берётся из функции `рекоменд_цена(букет_id)`.
6. Схема — ровно та, что в курсовой (листинги 3.1–3.6). Менять её нельзя без согласия пользователя.
7. Все запросы параметризованы через `%s` или `%(имя)s`.
8. Параметры подключения хранятся в `config.ini`.

**Не делаем:**
- авторизацию и роли пользователей;
- сетевой или многопользовательский режим;
- редактирование уже сохранённого заказа: его удаляют и оформляют заново, как в ТЗ;
- учёт партий и сроков свежести;
- ручное создание заявок на закупку: их формирует база;
- изменение схемы БД.

## 3. Схема БД (13 таблиц)

| Таблица | Что важно приложению |
| --- | --- |
| `категории` | `название` уникально, `коэф_наценки ≥ 1` |
| `поставщики` | `срок_поставки` в днях, больше 0, по умолчанию 1 |
| `растения` | `тип` CHECK, FK на категорию и поставщика, `остаток`, `мин_остаток` |
| `сотрудники` | `должность`: 'флорист' / 'курьер' |
| `клиенты` | `имя` NOT NULL, `телефон` UNIQUE NULL, `email` |
| `шаблоны`, `состав_шаблона` | книга рецептов; состав удаляется каскадно вместе с шаблоном |
| `заказы` | `клиент_id` и `способ_оплаты` (наличные/карта/перевод) обязательны. `курьер_id` NULL — самовывоз. `адрес_доставки`, `время_доставки`, `получатель`, `телефон_получателя` |
| `букеты`, `состав_букета` | `шаблон_id` NULL — индивидуальный букет. Если удалить шаблон, ссылка обнуляется (SET NULL) |
| `растения_в_заказе` | отдельные растения в заказе |
| `списания` | растение, количество, причина (увядание/брак/повреждение) |
| `заявки_на_закупку` | количество, `ожидаемая_дата`, `статус` (новая/выполнена/отменена) |

**Логика, которая уже есть в БД.** Приложение её только вызывает и не повторяет в Python:

- **`рекоменд_цена(id)`** — рекомендуемая цена букета.
- **Триггер `тр_склад`.** Висит на `состав_букета`, `растения_в_заказе` и `списания` и делает следующее:
  - проверяет остаток и при нехватке выдаёт ошибку «Недостаточно «…» на складе: есть N, нужно M»;
  - списывает растения со склада, а при удалении строки возвращает их;
  - подставляет цену, если она не передана;
  - после списания вызывает `проверить_запас`.
- **`проверить_запас` и `сформировать_заявки()`.** Сами создают заявки на закупку по точке заказа.
- **Триггер `тр_поставка`.** Когда заявке ставят статус «выполнена», он увеличивает остаток. Закрытую заявку изменить нельзя.

Что из этого следует для приложения:
- поле `остаток` вручную правится только в форме растения, например при инвентаризации;
- удалить заказ — это один `DELETE FROM заказы`;
- удалить списание — это его отмена;
- заявки могут появиться сами после продажи, и это нормально.

## 4. Подходы к построению интерфейса

Рассматривались три варианта:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **А. Общий класс «вкладка-справочник» + отдельные классы для сложных экранов** | 6 справочников описываются короткими настройками: колонки, поля, SQL. Код справочника пишется один раз | Нужно один раз объяснить на защите, как класс читает настройки |
| Б. Отдельный класс на каждую вкладку | Каждый файл читается сам по себе | Шесть почти одинаковых классов. Копипаста увеличивает код в 4–5 раз, а ошибки придётся чинить в шести местах |
| В. Формы в Qt Designer (`.ui`) | Окна можно рисовать мышкой | Лишние файлы и загрузка `uic`. Труднее показать код в записке |

**Выбран вариант А [моё решение].** Общий класс получается небольшим, около 150 строк, и его легко объяснить: «таблица берёт строки из `SELECT`, форма строится по списку полей». Сложные экраны пишутся отдельно, напрямую: книга рецептов, заказы, заявки, отчёты.

## 6. Модули

### 6.1. `db.py` (около 60 строк)

- **`connect()`** — читает `config.ini`, открывает одно соединение на всё приложение.
- **`fetch(sql, params=None)`** — выполняет `SELECT` и возвращает `(названия_колонок, строки)`. После чтения делает `conn.rollback()`, чтобы не держать открытую транзакцию.
- **`execute(sql, params=None)`** — одна команда записи в `with conn:`. Если в запросе есть `RETURNING`, возвращает значение.
- **`transaction()`** — отдаёт курсор внутри `with conn:` для нескольких команд подряд. Нужно для оформления заказа: всё фиксируется или откатывается целиком.
- **`error_text(e)`** — превращает `psycopg2.Error` в понятное сообщение по `e.pgcode`:

  | Код | Сообщение |
  | --- | --- |
  | `23503` (внешний ключ) | «Запись используется в таблице «…», удалить её нельзя» (таблица берётся из `e.diag.table_name`) |
  | `23505` (уникальность) | «Такое значение уже есть» + поле |
  | `23514` (CHECK) | «Недопустимое значение» + ограничение |
  | `23502` (NOT NULL) | «Не заполнено поле …» |
  | `P0001` (RAISE EXCEPTION из триггера) | текст самого триггера, он уже по-русски |
  | остальные | исходный текст ошибки БД |

- Любая ошибка ловится в интерфейсе: вызывается `QMessageBox.warning(…, db.error_text(e))`, и соединение возвращается в рабочее состояние. `with conn:` уже сделал rollback.

### 6.2. `sql.py`

Здесь все SQL-тексты, сгруппированные по экранам:
- для справочников — `SELECT` списка, `INSERT … RETURNING id`, `UPDATE … WHERE id = %s`, `DELETE … WHERE id = %s`;
- списки для выпадающих полей: категории, поставщики, растения, флористы, курьеры, клиенты, шаблоны флориста;
- книга рецептов;
- заказы, а также `INSERT` для букетов, состава букета и растений в заказе;
- заявки на закупку;
- 7 запросов отчётов;
- `SELECT рекоменд_цена(%s)`.

**Предварительный расчёт рекомендуемой цены.** Пока букет не сохранён, его нет в БД, а цену нужно показать. Её считает SQL-запрос по той же формуле, что и в функции:

```sql
SELECT COALESCE(ROUND(SUM(t.кол * р.закупочная_цена * к.коэф_наценки), 2), 0)
FROM unnest(%s::int[], %s::int[]) AS t(растение_id, кол)
JOIN растения р ON р.id = t.растение_id
JOIN категории к ON к.id = р.категория_id;
```

Python передаёт только два списка: id растений и количества. Сам расчёт делает база.

**Изменения в отчётах по сравнению с листингами:**
- **Запрос 1.** Берём предыдущий завершённый квартал, как в курсовой. Параметров нет.
- **Запрос 2.** Добавлен необязательный период: `(%(с)s::date IS NULL OR з.дата >= %(с)s::date) AND (%(по)s::date IS NULL OR з.дата < %(по)s::date + 1)`. Без дат запрос совпадает с листингом 3.8.
- **Запрос 3.** Жёсткие даты заменены параметрами, обе границы включительно: `з.дата >= %(с)s AND з.дата < %(по)s::date + 1`.
- **Запросы 4–7** — без изменений.

### 6.3. `ui/directories.py` — справочники

Один класс `DirectoryTab` (виджет вкладки) и один класс `RecordDialog` (форма). Каждый справочник описан словарём настроек:

- заголовок;
- SQL для списка, добавления, изменения, удаления и чтения одной записи;
- поля формы.

Каждое поле описывается так: `(колонка, подпись, вид, доп. данные)`. Виды полей:

| Вид | Виджет |
| --- | --- |
| `text` | `QLineEdit` |
| `int` | `QSpinBox` |
| `money` | `QDoubleSpinBox`, 2 знака |
| `choice` | `QComboBox` с допустимыми значениями из CHECK |
| `ref` | `QComboBox` с названиями; хранит `id`, список приходит из SQL |

Обязательные поля проверяются до отправки в БД. Остальные ограничения проверяет база, её ошибку показываем через `error_text`.

Кнопки вкладки: «Добавить», «Изменить» (также по двойному щелчку), «Удалить» (с подтверждением), «Обновить».

| Вкладка | Поля формы | Особенности |
| --- | --- | --- |
| Категории | название, коэф. наценки | — |
| Поставщики | название, телефон, срок поставки | — |
| Растения | название, тип, категория, поставщик, закуп. цена, остаток, мин. остаток | в таблице категория и поставщик показаны названиями; строки с `остаток < мин_остаток` подсвечены |
| Сотрудники | ФИО, должность, телефон | — |
| Клиенты | имя, телефон, email | пустой телефон сохраняется как NULL, иначе сработает UNIQUE |
| Списания | растение, количество, причина | дата ставится по умолчанию (`now()`). Удаление спрашивает «Отменить списание? Растения вернутся на склад». Нехватку на складе покажет триггер |

### 6.4. `ui/templates.py` — книга рецептов

- Вверху выпадающий список флористов, только `должность = 'флорист'`.
- Слева список шаблонов выбранного флориста с кнопками «Добавить», «Переименовать», «Удалить». При удалении предупреждаем: проданные по шаблону букеты останутся и станут индивидуальными.

### 6.5. `ui/orders.py` — заказы

**Список заказов.** Колонки: №, дата, клиент, флорист, курьер или «самовывоз», способ оплаты, сумма. Сумма = Σ цен букетов + Σ (количество × цена) отдельных растений, считается в SQL подзапросами, как в запросе 3. Кнопки: «Оформить», «Просмотр» (также по двойному щелчку), «Удалить» (с подтверждением «Заказ будет отменён, растения вернутся на склад»), «Обновить».

**Просмотр заказа**, только чтение:
- шапка заказа;
- таблица букетов: шаблон или «индивидуальный», сложность, время, цена продажи, рекомендуемая цена через `рекоменд_цена(б.id)`;
- состав выбранного букета;
- отдельные растения;
- итог.

**Оформление заказа**, диалог `OrderDialog`:

1. **Шапка:**
   - Клиент — выпадающий список с поиском по подстроке. Каждый пункт выглядит как «Имя — телефон», поэтому постоянного клиента можно найти, просто набрав номер. Рядом кнопка «Новый клиент…»: открывает форму клиента из справочника, сохраняет его и сразу выбирает. **[моё решение]**
   - Флорист (только флористы), способ оплаты.
   - Курьер: «— самовывоз —» или курьеры.
   - Адрес, получатель, телефон получателя, время доставки. Эти поля доступны только при выбранном курьере, адрес тогда обязателен.
2. **Букеты** — таблица с кнопками «Добавить букет», «Изменить», «Удалить». Букет редактируется в диалоге `BouquetDialog`:
   - шаблон: «— индивидуальный —» или шаблоны выбранного флориста. При выборе шаблона его состав копируется из `состав_шаблона`, и его можно изменить;
   - состав: растение и количество, можно добавлять и удалять строки, одно растение только один раз;
   - сложность (выпадающий список) и время сборки в минутах;
   - рекомендуемая цена пересчитывается SQL-запросом из 6.2 при каждом изменении состава;
   - цена продажи сначала равна рекомендуемой, её можно изменить.
3. **Отдельные растения** — таблица (растение, количество) с кнопками «Добавить» и «Удалить».
4. **Итог** — предварительная сумма заказа.
5. **«Сохранить»** — всё одной транзакцией `db.transaction()`:
   ```
   INSERT INTO заказы (…) VALUES (…) RETURNING id
   для каждого букета:
       INSERT INTO букеты (заказ_id, шаблон_id, сложность, время_сборки, цена_продажи) … RETURNING id
       INSERT INTO состав_букета (букет_id, растение_id, количество) …   -- цену подставит триггер
   INSERT INTO растения_в_заказе (заказ_id, растение_id, количество) …   -- цену подставит триггер
   COMMIT
   ```
   При любой ошибке выполняется ROLLBACK, и показывается сообщение, например о нехватке на складе. Диалог не закрывается, данные в форме остаются.

**Проверки до отправки в БД:**
- выбраны клиент и флорист;
- если выбран курьер, заполнен адрес;
- в заказе есть хотя бы один букет или одно растение;
- в каждом букете есть хотя бы одна позиция.

### 6.6. `ui/purchases.py` — заявки на закупку

- Таблица заявок: №, дата, растение, поставщик, срок, количество, ожидаемая дата, статус. Сверху фильтр по статусу, по умолчанию «новая».
- **«Сформировать заявки»** вызывает `CALL сформировать_заявки()`. Это замена pg_cron: в курсовой прямо сказано, что без pg_cron процедуру вызывает приложение. После вызова показываем, сколько заявок добавилось.
- **«Товар получен»** выполняет `UPDATE … SET статус = 'выполнена'`, а склад пополняет триггер `тр_поставка`. **«Отменить заявку»** ставит статус «отменена».
- Обе кнопки работают только для заявок со статусом «новая». Если попытаться изменить закрытую заявку, база выдаст ошибку, и мы её покажем.
- Вручную заявки не добавляются и не удаляются.

### 6.7. `ui/reports.py` — отчёты

- Слева список из 7 запросов.
- Сверху панель параметров. Её состав зависит от выбранного запроса:
  - запрос 2 — галочка «за период» и две даты;
  - запрос 3 — даты «с» и «по», по умолчанию с 1 января текущего года по сегодня;
  - остальные запросы без параметров.
- Кнопка «Выполнить», результат выводится в `QTableWidget`.
- Для запроса 6 результат показывается в текстовом поле с отступами (`xml.dom.minidom`, только форматирование). Там же кнопка «Сохранить XML…» открывает диалог выбора файла.

## 7. Тестовые данные (`тестовые_данные.sql`)

Тестовых данных в курсовой нет, пишутся заново. Их задача — чтобы ни один отчёт не был пустым и были видны интересные случаи:

- 5–6 категорий с разными коэффициентами, 3–4 поставщика с разными сроками поставки, около 20 растений обоих типов;
- 3 флориста, 2 курьера, около 8 клиентов, у части нет телефона;
- у каждого флориста 2–3 шаблона;
- около 60 заказов. Даты считаются **от текущей даты**, через `date_trunc(...) ± interval` **[моё решение]**. Так отчёты 1 и 5 не опустеют, когда бы ни показывали приложение. Заказы покрывают:
  - все месяцы прошлого года, кроме одного-двух, чтобы были видны нули в запросе 5;
  - прошлый квартал (запрос 1);
  - текущий год (запрос 3);
- среди букетов есть все три сложности, по шаблону и индивидуальные, а также отдельные растения в заказах;
- несколько списаний;
- начальные остатки подобраны так, чтобы после продаж через триггер 3–4 растения оказались ниже минимума (запрос 4) и появились автоматические заявки.

Данные вставляются обычными `INSERT` без `id`, через триггеры. Так скрипт заодно проверяет и сами триггеры.
